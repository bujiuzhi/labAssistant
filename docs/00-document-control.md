处理原则：

- 原始来源保持不修改，存入 `audit/sources/`。

- 正式决策更新到对应 `docs/` 文档，并在本文件追加记录。
- 不通过修改 Mock 数据来替代需求决策。

## 4. 架构决策记录

### ADR-001：采用模块化单体

- 状态：建议批准。
- 决策：Django + Django REST Framework 作为一个业务服务，按领域拆分 Apps；异步任务独立为 Celery Worker。
- 原因：首期团队规模和业务复杂度不需要微服务；单体事务更适合项目、实验、ELN、检测归档的一致性要求。
- 后果：必须保持模块边界，禁止跨 App 直接修改内部模型。

### ADR-002：采用同域 Session 认证

- 状态：建议批准。
- 决策：前端和 API 通过同一域名发布，使用 `HttpOnly + Secure + SameSite` Session Cookie 和 CSRF。
- 原因：系统为第一方 Web 应用，Session 易撤销、可审计，避免把令牌存入浏览器本地存储。
- 后果：反向代理必须统一域名；未来开放移动端时再增加 OIDC/OAuth2。

### ADR-003：文件进入对象存储

- 状态：建议批准。
- 决策：数据库只保存文件元数据，二进制内容保存到 S3 兼容对象存储。
- 原因：实验图片、谱图和报告体量不可预测，数据库和 `localStorage` 均不适合承载。
- 后果：必须实现预签名上传、哈希校验、访问鉴权和生命周期清理。

### ADR-004：归档 ELN 不可原地修改

- 状态：待业务确认。
- 决策：归档后只能创建修订版本，保留原版本、修订原因、操作者和内容哈希。
- 原因：电子实验记录需要可追溯，覆盖修改会破坏证据链。
- 后果：需要独立的修订流程和权限。

### ADR-005：前端严格复刻既有原型

- 状态：已批准。
- 决策：独立 Web 项目的信息架构、可见文案、视觉层级和交互入口严格复刻
  `/Users/bujiuzhi/Downloads/实验助手`。当前源码决定功能和数据口径，同页面最新 QA 截图决定视觉表现。
- 原因：用户明确要求按既有原型开发，通用后台布局不满足验收目标。
- 冲突处理：源码与截图不一致时，优先实现源码中的当前功能，再按截图恢复布局和视觉；无法判定时记录到
  `docs/12-prototype-fidelity-ledger.md`，不得自行发明新的业务入口。
- 后果：现有深色侧栏、工作台欢迎语、路由标签页和非原型菜单退出正式 UI；后端字段与种子数据按原型补齐，
  但认证、权限、审计和数据持久化继续采用独立项目技术方案。

### ADR-006：删除玄鉴宿主外壳

- 状态：已批准。
- 决策：独立 Web 项目不复刻玄鉴客户端品牌栏、交通灯、问题反馈、在线状态、左侧菜单和历史会话。
  页面只保留一条实验助手产品栏，承载产品品牌、三项业务导航和账户入口。
- 原因：用户明确项目只针对实验助手，玄鉴框架会造成产品边界错误。
- 与 ADR-005 的关系：ADR-005 继续约束实验助手业务页面、可见文案和关键交互；涉及宿主外壳的内容以本决策为准。
- 后果：浏览器标题、应用框架和验收台账统一去除玄鉴标识；账户退出能力从宿主侧栏迁移到产品栏右侧。

### ADR-007：首期 ELN 采用结构化 JSON 记录模块

- 状态：已批准。
- 决策：实验计划使用 `experiment` 聚合根；当前原型允许用户动态增删配方列、附加表格和过程模块，
  因此首期记录正文存入一对一的 `experiment_record`，使用受序列化器约束的 JSON 字段。
- 原因：原型字段结构由用户在运行时定义，首期若强制拆成固定列会丢失原型能力；将计划、状态、负责人和
  对象范围保留为规范化字段，可保证查询与权限稳定。
- 边界：JSON 仅用于配方列/行、附加模块、过程图片和附件元数据；实验编号、项目、负责人、状态、日期和版本
  不进入 JSON。过程图片首期作为受数量与总大小限制的数据 URL 保存，结果附件首期仅保存元数据。
- 后果：正式文件上传接入对象存储后，迁移 `process_images`、`result_files` 到文件对象和关联表；
  归档、修订和内容哈希进入下一阶段，已完成记录当前保持只读。
