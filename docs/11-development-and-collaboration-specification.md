# 开发与协作规范

## 1. 适用范围

本规范约束代码、文档、接口、数据库迁移、基础设施和审计资产的协作方式。业务和架构规则以对应专项文档为准。

## 2. 仓库资产边界

| 目录 | 资产职责 | 禁止内容 |
|---|---|---|
| `docs/` | 已纳入版本控制的正式规范 | 原始需求副本、临时会议附件 |
| `contracts/` | OpenAPI 和后续系统间契约 | 手工维护的重复前端类型 |
| `backend/` | Django 应用、迁移和后端测试 | 上传文件、生产数据 |
| `frontend/` | Vue 应用和前端测试 | `node_modules`、构建产物 |
| `data/` | DDL 导出、种子数据、导入模板 | 大型原始实验数据 |
| `audit/` | 来源、证据、派生审计和报告 | 正式业务代码、正式规范副本 |
| `infra/` | 容器、代理、监控和部署配置 | 明文密钥 |
| `scripts/` | 可重复执行的开发和运维脚本 | 无参数说明的一次性脚本 |
| `tests/` | 跨模块、契约和端到端测试 | 与业务模块重复的单元测试 |

同一类资产只保留一个正式来源。文件命名使用业务域前缀，例如 `experiment-import-template.xlsx`，禁止 `final-v2-new` 等版本堆叠命名。

## 3. Git 工作流

- `main` 始终保持可构建，禁止直接提交。
- 日常分支使用 `feat/<scope>-<summary>`、`fix/<scope>-<summary>`、`docs/<scope>-<summary>`。
- 分支保持短生命周期，避免多人长期共享开发分支。
- 提交信息格式为 `类型: 中文摘要`，类型使用 `feat/fix/docs/refactor/test/chore`。
- 一个提交只包含一个可解释变更；格式化和业务修改尽量分开。
- 禁止提交依赖目录、缓存、构建产物、大型原始数据、`.env` 和密钥。

合并请求必须说明：

1. 业务背景和变更范围。
2. 数据库、契约、权限和兼容性影响。
3. 测试命令及结果。
4. 页面变更的截图或录屏。
5. 迁移、发布和回滚注意事项。

## 4. 变更顺序

影响多个资产时按以下顺序处理：

1. 更新需求或架构决策，明确业务语义。
2. 更新数据字典和权限矩阵。
3. 更新 OpenAPI 契约并完成评审。
4. 编写数据库迁移和后端实现。
5. 根据契约生成前端类型并完成前端实现。
6. 补充测试、运维文档和变更记录。

紧急修复允许压缩评审时间，但不得跳过审计记录和回归测试。实现与正式规范不一致时，应修正其中一方并说明原因，不以“代码已这样实现”作为默认决策。

## 5. 代码审查检查项

### 5.1 通用

- 命名表达业务含义，没有无意义缩写和重复实现。
- 公共函数有类型和中文说明，关键路径有日志和异常处理。
- 没有明文密钥、个人敏感信息和调试输出。
- 新增依赖有必要性、许可证和维护状态说明，并锁定版本。
- 变更不覆盖或删除无关的现有资产。

### 5.2 后端

- 权限和组织范围在数据库查询阶段应用。
- 状态变更通过服务层执行，并包含事务、审计和并发控制。
- Serializer 不承担跨对象业务编排。
- 列表查询没有明显 N+1，索引与查询相匹配。
- 数据迁移可在生产规模内执行，说明回滚边界。

### 5.3 前端

- 使用 TypeScript 严格类型和 OpenAPI 生成类型。
- 页面具备加载、空、错误、无权限和只读状态。
- 敏感数据未写入浏览器持久存储。
- 未保存、自动保存失败和并发冲突可被用户明确感知。
- 固定工作台布局无主体双重滚动和内容遮挡。

## 6. 依赖与环境

- Python 使用同名 conda 环境和 `environment.yml`；命令显式使用 `python3` 或环境内解释器。
- 前端统一使用 pnpm，并提交锁文件。
- 依赖新增或升级前核对当前稳定版本、官方支持矩阵和安全公告。
- 开发工具版本在仓库中固定；CI 与本地使用同一主版本。
- 环境差异通过配置表达，不建立 `settings-final.py` 等重复文件。

## 7. 数据库变更

每个迁移必须：

- 有稳定、可理解的迁移名称。
- 明确新增或修改的表、字段、索引、约束和 COMMENT。
- 包含旧数据处理策略和数据质量校验。
- 说明锁表、耗时、空间和回滚风险。
- 在空库和上一发布版本副本上测试。

生产数据修复使用可重复脚本，支持 `--help`、范围参数、演练模式和执行摘要。脚本输出不得包含敏感正文；执行记录进入 `audit/` 对应发布目录。

## 8. 文档与决策

- 正式文档使用中文，标识符、字段名和代码使用英文。
- Mermaid 图与正文同时更新，不保留过期架构图。
- 重大技术决策追加到 `docs/00-document-control.md`，包含状态、原因、后果和替代方案。
- 已批准规范变更必须更新版本和变更记录。
- 原始需求和设计证据只归档到 `audit/sources/`，不直接修改。

## 9. 完成定义

一个功能只有同时满足以下条件才视为完成：

1. 需求范围、权限、数据字段和接口契约已确认。
2. 前后端实现、迁移和核心日志完成。
3. 单元、集成、端到端和越权测试按风险通过。
4. 文档、OpenAPI、部署配置和操作说明已同步。
5. 无阻塞发布的 P0/P1 缺陷和高风险安全问题。
6. 审查人可以根据变更记录定位新增资产并安全回退。
