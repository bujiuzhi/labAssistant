# 测试与验收规范

## 1. 质量目标

测试围绕“数据不串组织、权限不越界、实验记录不丢失、已提交证据不可被静默覆盖”展开。覆盖率是辅助指标，核心状态机、权限矩阵和并发路径必须以行为用例证明。

## 2. 测试分层

| 层级 | 工具 | 主要范围 | 执行时机 |
|---|---|---|---|
| 后端单元/服务测试 | pytest、pytest-django | 状态机、编号、校验、权限、查询范围 | 每次提交 |
| 前端单元测试 | Vitest | composable、格式化、表单规则、权限展示 | 每次提交 |
| API 集成测试 | pytest-django | 数据库事务、接口契约、对象存储适配 | 每次合并 |
| 端到端测试 | Playwright | 跨页面核心业务流程 | 每次合并及发布 |
| 契约测试 | OpenAPI 校验工具 | 语法、响应结构、破坏性变更 | 每次合并 |
| 性能测试 | k6 或同类工具 | 列表、保存、报告任务入口 | 候选发布版 |
| 安全测试 | SAST、依赖/镜像扫描、专项用例 | 越权、文件、会话、输入安全 | 持续扫描及发布 |
| 恢复测试 | 自动脚本与人工演练 | 数据库和对象存储恢复 | 至少每季度 |

## 3. 必测业务路径

### 3.1 项目与实验

1. 项目负责人创建项目、添加成员并激活。
2. 研究人员只能在参与项目中创建实验。
3. 从已发布模板创建实验后，修改模板不会改变已有实验步骤。
4. 实验计划缺少目的、步骤或负责人时不能提交。
5. 重复提交相同幂等键只产生一个实验或一次状态迁移。
6. 完成项目时仍有未完成实验应被阻止或明确确认，规则以产品决策为准。

### 3.2 电子实验记录

1. 实验开始后创建唯一 ELN 记录。
2. 自动保存使用版本号，正常保存递增版本。
3. 两个浏览器同时编辑时，后提交者收到 412，不覆盖先提交内容。
4. 提交生成内容快照，快照与提交时的步骤、材料和附件一致。
5. 退回后可继续编辑，但历史修订保持不变。
6. 归档后所有普通编辑接口拒绝写入。
7. 网络中断时页面不显示虚假的已保存状态，恢复后可重试。

### 3.3 检测与报告

1. 只有被指派检测人员能录入结果。
2. 录入人与审核人分离。
3. 数值、文本和结构化结果满足检测标准快照。
4. 已审核结果不能直接覆盖。
5. 报告保存输入快照和模板版本；同一幂等键不重复生成。
6. 异步生成失败后保存错误码，并可由有权限用户重试。
7. 报告下载重新校验当前权限，历史通知链接不能绕过权限。

### 3.4 文件

1. 超大小、禁止扩展名、声明 MIME 与实际类型不符时拒绝。
2. 未完成或未通过扫描的文件不能关联业务对象。
3. 用户不能完成、关联或下载其他组织的文件。
4. 上传地址和下载地址过期后不可使用。
5. 同一文件关联多个对象时，解除一个关联不删除文件实体。

## 4. 权限测试矩阵

每个受保护动作至少包含：

- 允许角色 + 允许对象范围：成功。
- 允许角色 + 不允许对象范围：404 或 403，且无数据泄露。
- 不允许角色 + 允许对象范围：403。
- 跨组织同 UUID 猜测：404。
- 对象状态不允许：409。
- 会话失效：401。
- 写请求无 CSRF：403。

测试数据必须至少包含两个组织、每个组织四类角色、参与和未参与项目、本人和他人实验。

## 5. 数据库测试

- 所有唯一约束、检查约束和外键均有失败用例。
- 精确数量边界、负数、超大值和单位换算有测试。
- 业务编号并发生成 100 次不重复且格式正确。
- 迁移在空库和上一个发布版本数据副本上执行。
- `eln_revision` 和 `audit_log` 的业务接口不存在更新、删除路径。
- 核心列表查询设置查询数量上限，防止 N+1 回归。
- 数据迁移校验处理前后行数、空值和枚举映射。

## 6. 非功能验收基线

以下指标基于 MVP 容量假设：单组织 200 活跃用户、5 万实验、单实验 50 个步骤，常态并发 50。上线前根据真实规模复核。

| 指标 | 验收目标 |
|---|---|
| 登录和会话恢复 | P95 不超过 800 ms |
| 项目/实验列表 | 20 条分页 P95 不超过 1 s |
| ELN 单步骤保存 | P95 不超过 800 ms |
| 普通写接口错误率 | 稳态压测低于 0.5% |
| 100 MB 文件上传 | 支持直传、进度和失败重试，不占用 Web 进程传输 |
| 报告任务受理 | 2 s 内返回 202，生成耗时通过状态查询 |
| 可用性目标 | MVP 月度 99.5%，计划维护除外 |
| 数据恢复点目标 RPO | 不超过 24 小时；正式生产建议收紧至 1 小时 |
| 恢复时间目标 RTO | 不超过 4 小时 |

性能结果必须记录数据规模、并发模型、环境配置和 P50/P95/P99，不能只记录平均值。

## 7. UI 验收

- 1280px 和 1440px 下无主体双重滚动、内容遮挡和大面积异常留白。
- 列表加载、空、错误、无权限状态完整。
- 100 行表格、长项目名、长实验步骤和 20 个附件布局稳定。
- 键盘可完成主要表单录入，焦点顺序合理。
- 表单错误与字段关联，颜色不是唯一状态线索。
- 离开未保存表单、并发冲突、保存失败都有持久提示。
- 支持的三类浏览器完成冒烟测试。

## 8. 发布门禁

候选版本必须满足：

1. Lint、类型检查、单元、集成、E2E 和契约检查全部通过。
2. 核心后端领域服务行覆盖率不低于 85%，整体覆盖率不低于 75%；不得通过排除关键文件达标。
3. 无未处理的严重和高风险安全问题。
4. 数据迁移在生产等比例样本上验证并估算锁表时间。
5. 备份、回滚和恢复步骤经过预发布环境演练。
6. 产品负责人、技术负责人和测试负责人完成验收记录。

## 9. 缺陷分级

| 等级 | 定义 | 发布要求 |
|---|---|---|
| P0 | 数据丢失、跨组织泄露、系统不可用 | 立即处理，禁止发布 |
| P1 | 核心流程不可完成、权限严重错误 | 候选版本必须关闭 |
| P2 | 有替代路径的功能错误、明显体验问题 | 明确负责人和截止日期 |
| P3 | 轻微显示或低频问题 | 可进入后续迭代 |

每个缺陷包含复现条件、预期/实际结果、影响数据、证据和回归用例；修复核心缺陷必须补充自动化回归。
